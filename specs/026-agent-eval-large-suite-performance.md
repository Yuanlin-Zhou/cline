# SPEC-026：大案例集与评测批次的交互性能优化

状态：Implemented / 已实施
日期：2026-10-26（北京时间）
基线：`work`，`59f3db8`（LLM Judge 已提交并推送）
提出依据：用户导入 200 个 10–200 KB 案例到本地 SQLite，启动评测、重跑评测、打开案例集及评测批次存在 3–5 秒响应延迟；用户要求生成修改 spec。
范围：agent-eval 的 Web 查询、SQLite 运行存储与队列、案例目录接口、前端数据加载、迁移和验证；兼容 SQLite/MongoDB 案例库。不修改 SDK、评测规则或模型调用协议。
确认记录：2026-10-26 用户回复“继续实施”，批准本方案及 MongoDB 兼容范围。

## 1. 目标与非目标

目标是让常用页面与操作的开销主要取决于当前显示的摘要和用户选中的内容，避免随所有案例正文、无关批次历史或重试次数一起增长。

- 打开案例集不下载所有 prompt、history、Judge 参考答案或运行配置正文。
- 打开批次不读取无关批次的执行 JSON，不一次下载全部尝试的输入、输出和证据。
- 运行时只同步变化的摘要；仅当前选中的执行获取进度或完整详情。
- 启动和重试只读取必要的案例/原始快照，保留校验、事务和幂等保证；提交后及时进入批次页面。
- 历史快照、全部尝试、会话、产物、原始响应、LLM Judge、费用和导出保持可追溯。

本期不更换数据库、不强制用户清理历史、不降低已保存证据或最终输出质量、不引入 Redis/SSE/WebSocket，不做多服务架构。暂不做历史快照去重或移动到外部文件；先消除不必要的读取与传输。压缩或纯前端分页不能代替本方案的数据访问修改。

## 2. 已调查的当前行为与证据

已阅读根目录及应用 AGENTS.md、`docs/agent-eval-intranet-roadmap.md`、SPEC-008/010/021/022/023/024/025，以及 store、catalog、MongoCatalog、queue、server、types、repeat-report、grading summary 与客户端加载/重试/轮询源码。

| 路径 | 当前开销 |
|---|---|
| `GET /api/state`（server.ts:78） | 读取全部执行记录和完整案例；返回完整案例正文及全部批次摘要 |
| `EvalStore.list`（store.ts:38） | 同步读取指定 kind 的全部 JSON 并逐条解析 |
| `EvalStore.items(runId)`（store.ts:152） | 先解析全部批次执行，再在 JS 中筛选 runId |
| 批次详情接口 | 返回全部尝试、完整案例快照、结果与报告；重试后体积继续增长 |
| `pollRun` | 每次响应结束约 1 秒后再次请求完整批次 |
| 启动路径 | 全量目录读取、两处案例解析、快照复制/写入；queue.kick 在首次异步等待前还会加载全部执行记录 |
| 重试路径 | 先取完整批次显示确认框，提交后整页重新获取完整批次 |
| 运行进度写入 | 每次持久化重新序列化整个 RunItem，包含不变的案例快照 |

独立模拟库复现（未读取用户内网数据库，未调用模型）：

- 200 个约 10–200 KiB 的案例，正文合计约 22 MB；含 20 条历史消息/案例。
- 新增 5 批历史、一次新建和一次重试后，1400 条执行记录约 155 MB。
- 列表请求约 22 MB；200 项批次详情约 22 MB；全量重试后同批次详情约 44 MB。
- 桌面 Chromium：打开案例集约 1.8 秒、批次约 1.5 秒、重试确认约 2.4 秒、新建评测页约 1.6 秒。
- 浏览器 CPU 限速 4 倍：新建评测页约 4.2 秒。该限速仅模拟浏览器 CPU，不代表用户硬件。
- 启用真实队列调度、使用不调用模型的等待执行器：200 项启动请求约 0.96 秒，其中加载 1600 条执行记录约 0.71 秒。

以上是诊断样本，不是已达到的优化指标。实际内网延迟还受历史规模、案例结构、磁盘和硬件影响。评测状态更新、JSON 序列化及页面渲染可能叠加；不能把全部耗时归因于 SQLite 单次 SQL 或模型请求。

## 3. 整体方案

将正常交互拆成三层：

```text
案例/批次页面 → 轻量摘要与变化游标
当前选中案例或执行 → 按 ID 获取完整详情
报告/导出/原始材料 → 用户打开时读取，按版本复用结果
```

摘要只保存呈现、筛选、聚合和定位所需字段。完整历史继续保存，禁止用摘要覆盖正式证据。SQLite 的查询通过独立列及索引定位，不能仍然加载全部 data 后 filter，也不能在列表读取时对每条大 JSON 使用 json_extract 临时生成摘要。

## 4. 案例目录与页面加载

### 4.1 摘要数据

新增 `CaseSummary`，包含内部 id、moduleId、revision、updatedAt、归档标记，以及名称、描述、标签、回放方式和必要的执行模型标识。内部 id 用于路由和操作，不新增到案例列表可见字段。

摘要不包含 prompt、history、functionCall.history、systemPrompt、断言/验证规则正文、Judge 参考答案、请求头、defaults 完整对象等。各字段的完整值和配置仍通过案例详情获得。搜索继续覆盖原有名称/描述/标签语义；不为提速静默截断参与搜索的值。

- 增加 `GET /api/cases?view=summary&moduleId=...`：返回当前可见案例摘要。首次以轻量摘要承载现有全部列表与跨筛选选择能力，不强制新增分页交互。
- `GET /api/modules?view=summary`：仅查询模块和案例计数，不通过完整 catalog.snapshot 获取模块。
- 标签候选独立查询，例如 `GET /api/cases/tags`，不为标签取回案例正文。
- 全局执行/Judge 设置沿用独立设置接口。
- `GET /api/cases/:id` 保留完整定义与 defaults；编辑、单项复制和调试时按需获取。
- 案例最近结果从本地执行摘要查询，可批量按 caseId 返回；不能再依靠全量执行 JSON。沿用当前最新尝试选择及未运行/取消过滤规则，包括重试已排队时的展示，不擅自改成只按 endedAt 选最后结果。

案例集、导入页、新建评测页、案例详情初始加载和模块弹窗全部移除对 `/api/state` 的依赖。案例详情不同时下载全部案例和当前案例两份正文。

拖选、Shift 连选、全选筛选结果、反选及隐藏选择计数沿用 SPEC-023；选择集合保存 ID，不复制正文。复制流程进入编辑时再读取选中案例，保留逐项 revision、草稿和预览指纹校验。不得因为懒加载而套用当前全局配置替换来源 defaults。

### 4.2 两种案例库

- SQLite：从独立案例摘要表查询，案例创建、更新、归档、导入、复制、移动、删除时与原记录在同一事务维护。
- MongoDB：使用字段 projection 查询摘要，不把完整文档传回服务端后再裁剪，不调用会解析全部正文的 caseFromDocument；新增摘要适配器校验其所用字段。选中案例完整读取时继续执行完整合同校验，批量事务、可见模块和归档规则保持不变。
- MongoDB 的运行历史仍在本地 SQLite，不改变 SPEC-008 的职责划分。新增摘要查询不擅自扩大外部数据库 schema/index 合同；如实施证明必须扩展，写入本 spec 并明确 prepare 步骤。

## 5. SQLite 查询与存储调整

保留 `records` 中完整案例和执行记录，新增有版本的查询/状态结构，示意如下，具体 SQL 在实施时落实：

| 表 | 作用及关键字段 |
|---|---|
| `eval_schema` | 本地存储版本、迁移完成标识 |
| `case_summaries` | case_id 主键；module_id、archived、稳定排序键及轻量摘要 data |
| `run_item_summaries` | item_id 主键；run_id、case_id、root_item_id、attempt、round、status、seq 及轻量摘要 data |
| `run_item_state` | item_id 主键、run_id、状态/阶段、session_id、活动/时间、有限实时文本、详情版本；不包含案例快照或完整结果 |
| `run_revisions` | run_id 主键、单调递增 revision、游标世代及聚合缓存版本 |

必需索引包括案例 module/archived/排序、执行 runId/排序、runId/rootId/attempt、caseId/最近执行排序、runId/seq、运行状态及轮次。用 `EXPLAIN QUERY PLAN` 验证热点查询使用索引，而不是把 JSON 解析搬到 SQL 全表表达式中。

- 针对 item 的 store 查询必须按 runId、itemId、caseId 或 rootId 定位。队列、批次详情、最近结果、重试预览、取消、重启恢复均改用专用方法。
- 摘要含状态、尝试关系、时间、Token/费用、Judge 简要分数和确定性判分聚合所需的紧凑字段；不含 result.text、toolCalls、证据正文或脚本源码。
- 输出一致性比较可保存按现有换行/首尾空白规则生成的 SHA-256，报告展开正文时仍读取原结果；不更改比较规则。
- 实时状态写入只更新小记录，不再每 250ms 重写完整输入快照。开始/阶段/session/终态仍立即持久化，文本和普通活动继续合并写入，终态强制刷入。
- 完整详情、兼容接口和导出通过专用方法组合原始记录与最新状态，不能把未更新的旧 records.item 状态直接暴露给调用方。
- 正式结果完成时，结果正文、状态、摘要、批次 revision 和终态落库必须原子提交。缓存只能加速，不能作为唯一事实来源。
- 成本累计全部尝试，状态/通过率使用各轮最新尝试；Judge 费用、试评分与原执行成本继续分离。投影不允许把未评分或未知费用转换成 0。

### 5.1 旧数据迁移

启动提供明确的迁移阶段：

1. 在开始接收读写业务请求和恢复队列之前，检查 schema 版本与单实例迁移锁。
2. 使用 SQLite 一致性备份机制保存迁移前快照；WAL 模式下不能直接复制一个正在写入的主数据库文件充当备份。
3. 首次按主键/rowid 分批读取原记录构造摘要与状态，控制单批内存；完整大 JSON 仅在迁移阶段读取一次，不在每次启动重建。
4. 幂等回填、核对记录数量/关联/关键统计，最后原子设置完成版本。中断后重试不产生重复记录，不提前开放部分索引数据。
5. 旧记录缺 rootItemId/attempt/round 的默认值沿用 SPEC-021；旧费用、Judge、会话缺失按原语义处理。
6. 异常行、备份失败、磁盘不足或校验不一致应给出可定位错误并保留原记录，不能跳过错误后假装迁移完成。

迁移不删除旧字段/证据文件，原链接和内部 ID 不变。迁移后禁止用旧版本直接写这个数据目录，否则摘要会失效；回退应停止服务后恢复备份，再启动旧版本。文档需明确该约束。迁移耗时单独记录，不计作日常点击延迟。

## 6. 批次概览、详情与增量同步

新增轻量 API，旧完整接口保持兼容：

| API | 内容/调用时机 |
|---|---|
| `GET /api/runs` | 批次摘要，使用执行摘要聚合，不加载完整运行记录 |
| `GET /api/runs/:id/overview` | 批次信息、统计、revision/cursor，以及每个 rootItemId 的最新执行摘要；不含完整 snapshot/result |
| `GET /api/runs/:id/changes?cursor=...` | 本批次变化的最新摘要、被替换执行关系及必要统计；无变化返回小响应 |
| `GET /api/runs/:id/items/:itemId` | 用户选中的执行完整输入、结果和诊断定位；按 ID 读取并校验批次归属 |
| `GET /api/runs/:id/items/:itemId/attempts` | 同一 root 的尝试摘要，供首次/重试切换，不读取每次正文 |
| `GET /api/runs/:id/items/:itemId/progress?version=...` | 仅选中运行项的变化状态与有限实时文本；无变更不重发文本，不包含静态输入 |
| `GET /api/runs/:id/report?attemptMode=latest\|first` | 打开多轮报告时获取；按批次版本缓存并正确失效 |
| `GET /api/runs/:id/retry-preview` | 批次 retryRevision、失败原因计数、候选 itemId/根关系及直接执行提示，不含完整输入 |

新静态路由必须先于通用 `:itemId` 匹配，防止 preview/changes 等被当作 ID。

增量一致性要求：

- cursor 包含本批次单调 revision 和数据库世代；批次信息更新、追加尝试和每次已持久化进度都推进 revision。
- 初始 overview、变更集合、聚合和返回 cursor 在同一一致性读快照内生成，避免并发状态更新丢失。
- 按 `(run_id, seq)` 查变化，只返回受影响 root 的当前最新摘要。多次变更可合并成一次最新状态；尝试关系保留，旧尝试详情仍可访问。
- 无效/未来/不同世代游标返回明确的需要重新同步标记；客户端重新获取 overview，不使用旧 cursor 静默跳过变化。
- 取消后直到相关项持久化终态才停止同步。服务重启的 interrupted/error、活动、费用与 Judge 阶段必须能通过 overview 恢复。
- 当前项完成或详情版本变化时，客户端获取一次完整详情；不能把最终结果和证据塞进每次 changes。

沿用顺序轮询，每次完成后约一秒再查 changes，不允许请求重叠。页面切换取消不再需要的请求；仅更新发生变化的行与当前详情，保持筛选、选中项、展开状态和滚动位置。

实时预览仍是有限片段，保留现有文本上限和“非完整会话”的说明；完整会话分页/下载及归档接口沿用。模型原始输出和证据不因摘要优化而截断。

## 7. 启动、重试与队列

### 启动

- 新建评测页只读模块/案例摘要及设置。提交仍发送 caseIds/moduleIds 和原有运行选项。
- 服务端按选定 ID/模块读取必要完整案例，一次请求内复用解析结果和所需验证器准备；移除 server/store 的重复解析，但不移除任何必要校验。
- 先完成配置/凭据/规则/模式/工作区校验，再原子创建批次、全部项及其摘要，禁止先返回已启动再发现案例配置无效。
- 快照准备只处理所选数据，较长的纯 JS 准备循环分段让出事件循环，避免其他操作一直等待。
- 提交完成后返回轻量批次标识。队列唤醒在后续事件循环调度，不在 HTTP 返回前同步加载历史；队列按本批次待执行 ID、轮次和并发槽逐项加载完整输入，避免预载无关批次和全部大快照。
- 不改变按轮执行、并发上限、工作区锁、任务超时与取消语义，不把模型执行/工作区准备纳入创建事务。

### 当前批次内重试

- 确认弹窗改用 retry-preview；按失败原因计数和选择仍遵循 SPEC-021。打开弹窗不下载全部历史输入。
- POST `/api/runs/:id/retry` 保留 requestId、expectedRetryRevision、itemIds/statuses 和原子事务；服务器重新核验最新项与原因，不信任客户端摘要。
- 查询候选通过轻量索引完成；仅为实际追加项读取首次冻结快照与验证脚本。案例库后续修改不能影响重试。
- requestId 幂等记录与追加项、状态、摘要及 revision 同一事务提交，重发不重复调用模型。
- 成功后保留页面，通过 changes/overview 更新状态，不清空整页并重拉大批次。
- “重复评测本批次”仍创建新批次并沿用原快照；只加载所选源快照，不扫描无关历史。

## 8. 统计、报告、兼容与错误处理

- SPEC-021 最新/首次、轮次、累计重试与费用口径不变；SPEC-022 的混合判定口径和折叠偏好不变；SPEC-025 的 Judge 阈值、输入隔离和独立成本不变。
- 聚合直接使用紧凑字段，不能为了一个总数反序列化全部输出。多轮报告按需构建，缓存按批次 revision 失效；选中结果所引用的正文从原记录读取。
- JSON/CSV/Markdown 导出保留现有字段、全部尝试及快照。导出可按本批次分批读取；不能从摘要重建并遗漏原字段，也不能读取无关批次。较大导出属于显式重操作，单独测量。
- `/api/state`、原批次完整 GET、旧 parentRunId 和详情链接保留，不静默改变响应结构；新版 UI 不再使用这些重接口做普通列表或轮询。其兼容实现也应避免无关批次正文扫描，完整响应仍可能较大。
- 详情请求/轮询失败保留已展示内容，提示同步失败并可重试；不能显示全通过或空列表冒充成功。
- 前端处理乱序响应、切换项后的旧响应、断线恢复、过期版本及浏览器后台再激活；新的详情不会被旧请求覆盖。
- 摘要不一致视为存储错误，提供显式重建与校验路径；不得在日常请求中静默退回全库扫描掩盖问题。
- 不新增 SDK 日志脱敏、联网服务、自动模型重试或隐式付费调用。

## 9. 性能与功能验收

### 9.1 可重复的测试条件

生成测试数据，不使用用户私有案例或模型凭据；保存种子、提交号、Bun/Node/浏览器版本、CPU/内存/磁盘、数据库/WAL 大小、并发和测试命令。

至少覆盖：

- 200 个 10–200 KiB 案例：正文分别主要位于 prompt、普通 history 和原生函数调用历史；固定短名称/描述与有限标签，避免靠单一重复字符串证明所有形态。
- 0、5、25 批历史，每批 200 项；混合通过/失败/错误/无法判定/取消、至少两轮全量重试。
- 小输出与较大原始响应/工具记录/判分证据/Judge 配置，SQLite 必测；可用 MongoDB 副本集时执行其摘要和完整读取兼容测试。
- 并发 1/4，慢模型无输出、持续文本、验证中和 Judge 评分中；本地模拟执行器/Provider 保证不产生付费请求。

性能以同机浏览器访问本机服务、无外部网络延迟、迁移完成/预热后至少 30 次操作的 P50/P95 为主要指标；浏览器 CPU 限速 4 倍另测。冷启动、首次加载 JS、首次迁移单列，不与热路由切换混算。先后两版用相同数据/条件比较，不能仅凭更强硬件宣称达标。

### 9.2 目标与结构性门槛

| 指标 | 验收目标 |
|---|---|
| 200 项案例摘要响应 | 固定测试元数据下不超过 256 KiB，不含案例正文 |
| 200 项批次 overview | 固定测试元数据下不超过 512 KiB，不含完整快照/结果；增加旧尝试不线性放大 |
| 没有状态变化的 changes | 响应体不超过 2 KiB，不重发案例或文本 |
| 普通案例集/批次热导航、重试弹窗 | 桌面 P95 ≤ 800ms；4 倍 CPU 限速 P95 ≤ 1.5s |
| 创建 200 项/重试 200 项的 HTTP 响应 | 本地基准 P95 ≤ 1s；不含模型执行或工作区复制；所有持久化与校验仍须完成 |
| 交互即时反馈 | 桌面点击后下一帧/加载反馈 P95 ≤ 100ms；不等大请求完成才反馈 |
| 历史规模增长 | 从 5 到 25 批历史，读取指定同规模批次的热请求 P95 增幅目标 ≤ 20%；同时证明未读取无关正文 |

相对指标受计时噪声影响时增加样本并记录原始分布；不能靠隐藏同步错误或提前返回成功达标。绝对指标未达标时记录 CPU/SQL/序列化/浏览器长任务占比和差距，不自行降低标准。

结构性门槛比单次毫秒数更重要：用 SQL/存储方法计数、响应字段检查及查询计划证明列表/overview/changes/重试预览不读取正文；读取一个批次不解析无关批次 item。浏览器记录请求数量、传输/解析/渲染耗时与 Long Tasks。检查 200 KiB 案例不会在正常未变化轮询中反复传输。

### 9.3 正确性验收

- 新旧存储迁移幂等、失败回滚/恢复、一致性备份及重建；迁移前后各状态、首次/最新统计、成本、Judge 和导出一致。
- 重试两个页面并发、过期 revision、重复请求、网络结果未知、重启和取消，无重复任务或丢失历史。
- cursor 并发更新、无变化、多次变化合并、终态、世代不匹配及断线恢复，不丢状态，不停止过早。
- 多模块拖选、筛选隐藏项、复制时编辑配置、案例被更新/删除、直接工作区提示和冻结验证器行为不退化。
- 选中项、旧尝试、输入快照、会话、产物、原始输出、LLM Judge 正式/试评分均可查看；只有选中项按需读详情。
- 原有相关回归、类型检查、Web 冒烟和真实浏览器桌面/390px/键盘验证通过。既有 importable-examples 两项断言漂移及已发现的 SDK 启动时序不稳定单独记录，不计作性能优化成果。
- 没有真实 MongoDB 或模型服务的验证需明确记为未覆盖，不把模拟结果写成真实环境通过。

## 11. 实施与验证记录（2026-10-26）

已完成：

- SQLite 独立案例/执行摘要、实时状态、批次版本及索引；完整输入/结果继续保留。首次启动自动一致性备份、分批迁移和关联/数量校验；再次启动只检查索引记录一致性，不重解析大 JSON。提供停服重建工具，并阻止同一目录重复启动及在线重建。

- 批次概览、按 ID 详情/尝试/进度、重试预览、变化游标及按需报告。游标包含数据库及服务实例世代，重启/重建/无效游标重新同步；未变化时不重发输入、不重建整批 DOM。

- 重试保持原批次、冻结快照、失败原因选择、版本与 requestId 幂等；成功后局部同步，首次/最新尝试可切换。完整旧接口和导出保留。

量化结果（独立生成数据、本地模拟、不调用模型）：

- 200 案例摘要最大约 104 KB，200 项批次概览约 181 KB，无变化响应 101–103 字节；分别低于 256 KiB / 512 KiB / 2 KiB 目标。
