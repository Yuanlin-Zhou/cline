# SPEC-013：判定规则区域整体 UI review 与后续改进建议

- 状态：**Draft / review 已完成，后续功能改动待确认**
- 日期：2026-10-10（北京时间）
- 来源：用户批准 SPEC-012 后，要求重新 review 判定规则全部 UI，确保用户清楚下一步要做什么。
- 范围：案例“判定规则”页、最终回复检查、验收开关、规则选择/添加、全部内置文件规则、注册程序、Python/兼容脚本、行为诊断、整体 JSON 编辑、错误提示，以及相关验证结果呈现。
- 此文档记录问题与具体方案，除 SPEC-012 已批准的脚本 UI 外，不在本轮改动其他区域的功能。

## 1. Review 结论

页面目前按数据结构组织，而非按用户目标组织。最主要的问题是用户尚未选择“检查什么”，就看到所有输入项；常见任务和高级能力同层呈现；运行模式限制、判定层级和失败原因出现得太晚。仅整理 Python 区域不足以让整个页签好用。

理想路径：选择检查目标 → 填写最少必要内容 → 看懂通过条件 → 保存并运行 → 在结果里看到哪里不符和怎么修正。默认不必理解 protocolVersion、规则 ID、JSON Pointer、environmentId 或判分覆盖率。

## 2. 逐项问题与整改方案

| 区域 | 当前问题（源码位置） | 建议 | 优先级 |
| --- | --- | --- | --- |
| 整体入口 | app.ts 的最终回复检查默认显示所有大文本框；grading-editor.ts 的验收区域还有单独开关、选择器和两个添加入口 | 顶部展示简短说明“没有内容规则时只检查正常结束”；提供三个目标入口：最终回复、文件产物、自定义脚本。每个入口说明适用场景，新增后才显示对应表单 | 高 |
| 最终回复检查 | 包含/不包含/正则始终并列，“结束状态”有较长推荐说明且与实际默认值容易混淆 | 常用包含文字优先；不包含与正则按需添加，结束状态置于高级设置。保留每行一项与所有项同时满足的明确提示；现有值不能因收起而消失 | 高 |
| 判定关系 | 必须满足、启用验收、最终回复断言、结束状态分属不同区块，用户难判断哪些决定通过 | 页面统一说明“所有必要检查通过才算通过”；每张规则卡显示“影响通过 / 仅作参考”；编辑时提示至少保留一项必要验收规则；禁用后说明保留配置但不执行 | 高 |
| 模式约束 | setMode 只切换提示，单轮仍能选择文件规则，到保存时才报模式不符 | 文件入口就地显示“需要完整任务”；提供切换方式。模式切换不删现有规则，但逐条标出不兼容项，告知修改方法。注册程序和非 Python 脚本同样提前说明限制 | 高 |
| 规则选择 | 同一区域同时有“添加规则”和“添加此示例规则”，旁边长篇填写例子与通过/失败对照 | 主操作只保留“添加检查”；示例进辅助入口，明确是插入新规则。选择时只显示用途和最短例子，已添加卡片内仅提供本条相关帮助 | 高 |
| 文件存在/不存在/未改动 | 相同 reports/summary.json 占位，用户不易区分产物目录与本机目录；未改动规则涉及初始文件但只有说明 | 用具体业务名称“交付文件存在 / 禁止生成指定文件 / 初始文件保持不变”；各自短示例。默认只填一个相对文件路径；显示自然语言通过条件，明确不支持通配符与目录 | 中 |
| 文件文字 | 正则与文本包含同层，判断方式帮助含不同数据类型的泛化说明 | 显示仅适用于 UTF-8 文件的说明；根据判断方式显示专用提示和最小正反例；正则按需选择，保存前错误定位到表达式 | 中 |
| JSON 检查 | JSON Pointer、值类型、字段存在、近似误差各有说明，信息长且分散 | 按“文件 → 字段 → 判断 → 期望”排列；默认简单字段例子，复杂路径折叠。等于时显示值类型；存在时隐藏期望；近似时优先绝对误差，相对误差高级展开；动态自然语言摘要不出现 irrelevant 字段 | 高 |
| 注册验收程序 | 与用户上传脚本共用列表，可误选不合适程序；无程序时不知道去哪配置 | 明确标注维护者配置能力，不让普通用户填命令；筛选/说明可用程序，空列表引导使用内置文件规则或上传 Python，避免虚构示例程序 | 中 |
| Python/兼容脚本 | 长教程、上传、参数、完整性矩阵与历史测试堆在卡片里 | 按 SPEC-012 实施紧凑选择区、上传弹窗、独立指南、折叠高级设置及试验证面板 | 已批准实施 |
| 行为检查 | 不可判分但仍有四种类型、JSON 输入与示例，用户可能花时间配置无法使用的必要条件 | 默认仅展示“当前暂不支持真实工具行为判分”；已有诊断配置可在“查看已有诊断配置”内编辑。新增诊断作为高级能力，清楚说明仅作参考；不改变现有不支持语义 | 高 |
| 规则 ID/名称 | 高级入口含规则 ID，未命名结果以 rule-1 呈现，用户定位困难 | 自动展示业务摘要，例如“out.txt 包含 hello world”；显示名称可选，内部 ID 只在高级详情里出现。重复 ID 错误定位到对应规则 | 中 |
| 整体 JSON | “载入当前规则 / 应用 JSON”会让用户不清楚编辑了哪个版本，“应用”也可能替换已有表单 | 明确是高级替换操作；显示有待应用变更，应用前提示将替换当前规则，失败保留原内容，成功提示已应用且仍需保存案例 | 中 |
| 校验与反馈 | 控件 blur、卡片 focusout、通过条件预览均校验，未完成填写时可能出现一片“待补充”；跨规则/模式错误集中在页底 | 以保存/运行前校验为主，填写时给短提示；错误靠近对应项，自动展开并定位首个错误，顶部汇总存在几项待修正；不得因点击教程/上传造成错误插入并移动点击目标 | 高 |
| 结果展示 | grading.ts 对缺省 expected/actual 也显示占位，checks 内容平铺，证据重复点击不断追加；结果名称和 hash 优先级不合理 | 首先显示结论与失败原因，必要条件摘要；逐条卡片用中文业务标题，只有有值才显示预期/实际；证据按需载入复用区域，执行指纹/规则版本折叠到详情；日志异常附建议动作 | 高 |
| 窄屏与键盘 | 部分按钮没有分组间距，多个操作容易挤满一行；需要完整键盘验证 | 统一操作行 gap/自然换行，限制长代码/JSON 高度与宽度；所有可编辑控件有标签和错误关联；弹窗支持 Escape、焦点约束与关闭后焦点返回；状态中文化 | 高 |

## 3. 建议后的页面结构

```text
判定规则
所有必要检查通过，才算本次评测通过。

添加检查
[最终回复]  [文件产物 · 完整任务]  [Python 脚本]

已有检查
  最终回复包含指定文字        影响通过
  out.txt 存在               影响通过
  Python 文件业务检查         影响通过

高级设置 ▸（结束状态 / 注册验收程序 / 已有行为诊断 / 整体 JSON）
```

最终回复规则暂仍存 assertions，文件/脚本规则仍存 grading.rules；可以统一视觉，但不能为改布局而无声转换数据和判分语义。启用/禁用与 required 的现有约束必须保留。用户没有内容判定时，应准确说明系统默认结束状态检查，而不能承诺验证了业务完成。

## 4. 数据兼容、异常与边界

本建议不增加判分能力、不修改 SDK，不改变 MongoDB/SQLite 结构；仅通过当前数据读写路径改 UI。旧案例所有 assertions/grading 配置（含隐藏项）应原样载入和保存。更改规则类型不得静默丢失配置；模式切换不自动删规则。列表、上传、试验证、输入和日志各自有加载/错误/重试状态，保持已填写值。大字段预览截断要标注，下载仍提供完整数据。

未保存的案例调试执行使用独立 draft 身份，目前不会进入该已保存案例的历史列表；UI 必须明确提醒“先从案例列表运行已保存案例”，不能泛称“先评测一次”让用户反复调试仍找不到历史。将 draft 与案例关联属于单独的数据行为变更，未在本方案要求。

## 5. 后续实施与验收（待确认）

1. 先统一入口、最少填写项、模式限制和必要条件说明，保持旧配置往返兼容。
2. 再整理五种文件规则、回复规则和注册程序帮助，把无效行为能力移到高级诊断。
3. 整理结果页的结论、预期/实际、检查项和证据，使用户能从失败原因返回修改对应规则。
4. 浏览器按首次使用路径验收：单轮回复检查；完整任务文件/JSON 正负例；高级配置保存再打开；不兼容模式、空列表、错误 JSON 和重复规则 ID；已有案例和诊断不丢失；窄屏/键盘操作。
5. 对涉及状态和保存兼容的逻辑进行必要测试，运行类型检查；更新相关文档和本方案验证记录。

本轮已确认的是 SPEC-012 的 Python UI 改造与此 review；本表其他区域的实现需确认后续方案。
