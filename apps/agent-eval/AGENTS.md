# agent-eval 开发约定

本目录遵循仓库根目录 AGENTS.md。以下约定来自用户于 2026-09-16 的明确要求，适用于 agent-eval 的后续功能开发和行为变更，包括为其修改的共享代码。

## Spec 优先

1. 开发前先阅读相关 roadmap、已有 spec 和当前源码。按用户于 2026-10-08 的最新要求，每项独立功能或行为变更必须在**仓库根目录 `specs/`** 新建设计方案；实现和验证记录更新对应方案。历史本目录 `specs/` 文档保留，不迁移。
2. Spec 至少包含：目标与范围、当前行为、方案与接口/数据变更、兼容性、异常处理、验收标准和实施步骤。
3. 新方案标记 `Draft / 待用户确认`；向用户提交具体方案后，等待用户明确确认，再修改实现代码。用户要求“继续”编写方案，不等于批准开发。
4. 用户确认后记录确认日期和范围，将状态改为 `Approved`，按该范围实施；不重复请求已经获得的确认。
5. 实施中若需实质改变范围、外部行为或核心设计，先更新 spec 并确认变更；已批准范围内的常规实现细节自行处理。
6. 完成后补充验证结果和偏差，将状态改为 `Implemented`。不把 roadmap 中的建议或示例当作已经批准的开发任务。
7. 用户在当次会话明确要求跳过或调整流程时，以用户最新指令为准。

仅阅读、调查、编写方案及维护本约定可直接执行。不要在方案阶段混入功能实现或提交此前无关改动。

## 前端改动必须复核实际 UI

用户于 2026-10-29 明确要求：**每次修改前端，都必须复核 UI 实现**。这是交付要求，不能只靠类型检查、构建成功、DOM 断言或“截图已生成”判断完成。

- 在浏览器打开最终代码，走通被修改的用户流程；至少检查桌面与窄屏实际界面，并亲自查看截图。
- 覆盖相关的空状态、错误/重试状态，以及短内容、长内容；检查信息归属、控件对齐、间距、内容高度、换行和溢出。
- 同一错误应更新同一个提示区域，不能因重复点击而堆叠；请求进行中须避免重复提交。错误内容必须说明真实问题，不能用数量限制代替结构错误。
- Bad case 属于案例属性，标识放在案例名称附近；回放方式列只展示回放方式。错误输出默认紧凑，长内容可展开/滚动，不能为一行文本保留大块空白。
- 记录复核页面、状态、截图路径与发现/修复的问题。发现明显 UI 问题先修复再交付；未能完成浏览器复核时，明确说明缺少的验证，不能宣称已完成 UI 验收。
