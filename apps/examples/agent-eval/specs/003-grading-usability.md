# SPEC-003：让首次使用者能独立填写结果判分规则

- 状态：**Implemented / 已实施**
- 确认记录：2026-09-16，用户在具体方案确认请求后回复“继续”，批准按本方案实施。
- 日期：2026-09-16
- 来源：用户反馈不知道规则如何填写、缺少示例及正确性判断，要求从用户角度优化。
- 关联：SPEC-001、SPEC-002。

## 1. 目标与范围

让首次使用者不读文档、不接触规则 JSON，即可选择常用结果规则，按示例填写，并理解何时通过。覆盖全部七种结果规则及文本/JSON 的每种比较方式；行为规则仅明确能力限制，保留既有编辑入口。

沿用现有界面组件与视觉规范，不修改 SDK、判分引擎、服务端接口、统计口径或已存案例。

## 2. 当前问题

- 类型下拉框只有技术名称，无法从“我要检查什么”判断选择。
- 新规则自动写入 output.json、12 等示例值，没有区分示例和用户要求，容易误存。
- JSON Pointer、JSON 预期值和容差需要用户预先懂技术；placeholder 输入后消失，不能作为完整说明。
- 现有示例案例与编辑位置分离，没有逐项填写示范及通过/失败对照。
- 字段错误集中出现在区域底部，常含 grading.rules 索引；用户难以知道改哪个输入。
- 验证器空列表没有解释下一步；不支持的行为规则与可用结果规则并列，增加初学负担。

## 3. 用户流程与界面

### 3.1 先选目标，再填参数

入口文案为“你想检查什么？”，提供带简短用途说明的选择项：

- 生成了指定文件：确认交付物存在。
- 没有留下指定文件：禁止临时文件或额外产物。
- 原有文件没有被修改：保护配置或输入文件。
- 文件里包含／不包含指定内容：检查说明文档、代码或文本。
- JSON 中的数据符合要求：检查统计值、字段、数组成员。
- 运行已配置的验收程序（高级）：按退出码判断。
- 使用已配置的验证脚本（高级）：按脚本返回结果判断。

选择后立即显示用途与填写示例，再添加规则；行为规则放入独立的“行为检查（当前不可判分）”折叠区域，既有规则仍可查看和编辑。

启用区明确：“检查 Agent 运行结束后的工作区文件。只回复‘已完成’不代表通过。若要检查最终回复文字，请使用上方文本断言。”同时说明需要完整任务模式；模式不符时给出修改位置，不自动更改模式。

### 3.2 每条规则使用相同结构

1. 目标标题和一句用途说明。
2. 需要填写的字段；字段下常驻简短说明和例子。
3. “查看填写示例”：完整字段值、一个通过例和一个失败例；“添加此示例规则”创建新规则，不覆盖正在填写的规则，标注需要改成自己的要求。
4. 自动更新的“通过条件”自然语言摘要；无效或缺失字段显示“待补充”，不误报已通过。
5. 就近字段错误和修正建议。

普通添加生成空白业务字段，示例只显示为提示；必要条件默认开启。示例按钮才写入示例参数，ID 自动生成。复选框文案为“必须满足才算通过”，解释“取消后仅供诊断，不影响任务通过；至少保留一条必要规则”。已有文本断言也参与判定，必要项失败或无法判定不能被描述为通过。

### 3.3 JSON 填写示意

```text
JSON 中的数据符合要求                     ☑ 必须满足才算通过
用于检查生成的 JSON 文件中的具体数据。

文件路径       [summary.json                     ]
从工作区根目录填写，例如 reports/summary.json；不要填写电脑绝对路径。

要检查的字段   [/total                           ]
示例：{"total":12} 填 /total；嵌套字段填 /summary/total；数组首项填 /items/0。
留空检查整个 JSON。特殊字段名的写法放在“更多路径示例”中。

判断方式       [等于 ▼]    值的类型 [数字 ▼]
期望的数字     [12                                ]

通过条件：summary.json 能解析为 JSON，且 total 是数字 12。
通过示例：{"total":12}    不通过：{"total":"12"} 或 {"total":10}
```

预期值类型选择提供文字、数字、是/否、空值、数组/对象。文字直接填 Bun，无需用户添加 JSON 引号；数字输入保留数字类型；布尔值用选择控件；null 无额外输入；数组/对象才使用 JSON 编辑并给出示例。读取既有配置按原类型展示，切换类型不静默猜测或丢弃输入；转换失败保留草稿并就近提示。不同比较方式只展示适用控件。

## 4. 全部规则的填写示例与真实语义

| 规则／方式 | 填写示例 | 通过／失败及说明 |
|---|---|---|
| 文件存在 | 路径 reports/summary.json | 结束时该普通文件存在通过；不存在失败。目录不算文件，存在不代表内容正确。 |
| 文件不存在 | 路径 debug.log | 结束时不存在通过；存在失败。只检查指定路径，不支持通配符。 |
| 文件未修改 | 路径 config.json | 运行前后均存在且内容完全一致通过；新增、删除、修改都失败。提示需在初始工作区准备此文件。 |
| 文本包含 | README.md；包含；Bun | “使用 Bun 安装”通过，“使用 npm 安装”失败；区分大小写，不自动去空白。 |
| 文本不包含 | README.md；不包含；npm | “使用 Bun 安装”通过，“使用 npm 安装”失败；文件缺失也失败。 |
| 文本正则 | version.txt；正则；^v[0-9]+$ | v12 通过，version12 失败；直接填写表达式，不加 / 包裹，不填标志位；默认区分大小写，匹配整段需自行加锚点。 |
| JSON 等于 | summary.json；/total；数字 12 | 12 通过，字符串 "12" 失败；数组顺序影响相等，对象按完整值比较。 |
| JSON 字段存在 | summary.json；/total | 有 total 字段即通过，包括 null、0、false；字段缺失失败，无需填写预期值。 |
| JSON 包含 | summary.json；/items；文字 Bun | ["Bun","Node"] 通过，["bun"] 失败。数组检查一个完整成员，不是数组子集或对象局部匹配；字符串检查子串，对象不支持此比较。 |
| JSON 正则 | summary.json；/version；^v[0-9]+$ | 字段值 "v12" 通过，数字 12 失败；必须是字符串，表单直接填写表达式。 |
| JSON 数值近似 | summary.json；/ratio；数字 0.3333；最大绝对误差 0.001 | 0.3334 通过，0.34 失败；至少填写一种误差，不能为负。相对误差放在更多设置中，0.01 表示 1%。两者同时填写按较宽者判断，公式见说明。 |
| 验收程序退出码 | 从真实注册列表选择；期望退出码 0 | 实际退出码 0 通过、1 失败。说明通常 0 代表正常结束；不能在此输入 shell 命令。 |
| 独立验证脚本 | 从真实注册列表选择 | 正常返回约定格式且 verdict=pass 通过；verdict=fail 失败；脚本异常或返回格式错误显示验证错误，退出码 0 本身不代表通过。 |

JSON 路径补充：留空代表整个 JSON；/items/0/name 代表首项的 name；字段名含 / 时写 ~1，含 ~ 时写 ~0。不支持 $.total 或 total 的点路径写法。

误差公式与当前实现一致：实际值与预期值差的绝对值 ≤ max(绝对误差, 相对误差 × |预期值|)。预期值为 0 时，相对误差不能提供非零允许偏差。

## 5. 异常处理与兼容性

- 路径空白、绝对路径、上级目录、无效 JSON 路径、非法数字、无效正则、缺少容差等在失焦和保存时就近提示；提交时定位首个错误并聚焦，aria-invalid/aria-describedby 关联提示。
- 字段保留已输入内容，不因添加、删除、示例、切换比较方式或验证器异步加载丢失草稿。类型切换保留各类型草稿；只有当前选中类型写入配置。
- 摘要只解释配置，不执行 Agent、不冒充试运行结果。完整 JSON 导入继续交给现有 schema 校验，错误转为规则名称/序号和字段中文提示，保留详细原始信息入口。
- 验证器显示加载中、加载失败可重试、列表为空、已保存 ID 未注册四种状态。空列表提示“当前没有可用验收程序，请联系维护者注册，或选择文件/JSON 检查”，不虚构可选择的验证器。
- 现有行为规则显示用途和“当前不能验证真实工具行为；可选规则只会显示证据不足”，不把示例包装成已可运行能力。必要行为项明确提示阻止运行。
- 保存格式仍为 grading version 1；原有 ID、label、required 和合法参数保持兼容。高级整体 JSON 编辑继续保留，默认折叠。
- 不覆盖用户案例、不再次批量导入既有示例、不触发模型调用。

## 6. 验收标准

1. 新用户能在界面找到每种结果规则的用途、字段填写例、通过及失败对照，无需打开外部文档。
2. 从空规则开始，按引导独立完成“summary.json 的 total 必须为数字 12”，保存重开类型和值保持一致。
3. 覆盖五种 JSON 比较方式和三种文本比较方式；示例严格匹配引擎实际语义。
4. 故意填写错误时，错误在对应输入附近并说明如何改，原输入不丢失；包含添加/删除、切换方式及异步加载场景。
5. 所有七种结果规则、必要/可选状态和高级编辑保持保存重开兼容；普通添加不把示例值当用户配置。
6. 桌面和窄屏检查层级、换行、可读性、键盘操作和错误聚焦；浏览器不可用时如实记录未验收项。
7. Bun typecheck、相关 grading/Web 回归测试通过；补充预期值转换与保存保真的必要测试，防止数字/字符串混淆。

## 7. 实施步骤

1. 用户确认此方案后记录确认范围和日期，状态改为 Approved。

3. 完成类型化预期值输入、条件摘要及字段错误定位；完善验证器与模式提示。
4. 按验收标准检查保存重开及回归，补齐视觉验证记录，更新状态为 Implemented。
