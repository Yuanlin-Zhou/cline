# 内网魔改 Cline Agent 评测：功能设计与交付路线

日期：2026-09-16。本文整合本轮讨论，基于当前仓库源码、内网迁移记录和已查阅的官方资料。文中的新增功能、报告示例和交付目录均为设计建议，尚未实现；外部框架能力以所引用版本的文档和源码为准。

## 建议结论

建议先扩展现有 agent-eval，形成“运行真实的魔改 Agent → 模拟必要交互 → 验证工具行为和最终产物 → 对比版本”的回归闭环，保留现有 Web、案例管理及批次执行能力。

本轮讨论的重点是：**结果与行为判分可靠，以及同事无需搭建开发环境即可使用。** 建议首期交付 Windows 便携包，支持解压双击启动和预置标准案例；后续根据团队规模增加内网集中部署。

最关键的问题是：**测到的必须是你们实际交付的 Agent 行为，不能只测模型回复，也不能被评测器固定的系统提示词、审批和工具策略覆盖。**

## 当前基础与缺口

当前已有 JSON/JSONL 案例导入、历史上下文、单轮/完整任务执行、批次并发与取消、配置快照、工具调用结果和文件差异展示。Web 执行为每个案例创建独立 worker、数据目录和工作区副本。

主要缺口：

- Runner 直接创建 `ClineCore`，设置评测专用系统提示词与工具策略；需要确认魔改功能是否真正经过这条调用链。
- 允许的工具自动批准，进入审批回调的请求直接拒绝；没有补充信息后续跑的协议，`history` 不是对话脚本。
- Skill/MCP 没有案例级配置；常规 MCP settings 加载被关闭，Web 工作区复制还会排除 `.cline`。
- 自动判分仅检查最终文本和结束原因；工具记录、文件差异目前不能直接证明任务成功。
- 已有离线打包与冒烟基础，但发布包不包含全部第三方依赖；内网自定义 HTTP Headers 尚未接入。

### 当前交互与工具模式的准确边界

| 配置或场景 | 当前行为 |
|---|---|
| `single-turn`，包括未填写回放模式 | 强制禁用工具，只生成一次模型回复 |
| `full-task` + `none` | 不开放工具 |
| `full-task` + `read-only` | 仅允许 `read_files` 和 `search_codebase`，自动批准 |
| `full-task` + `full` | 使用 `yolo` 模式，开放的工具自动批准；仍进入审批回调的请求直接拒绝 |
| 需要用户补充信息 | 非交互运行，默认提示词要求不要询问交互输入；没有自动应答和续跑流程 |
| Skill | 沿用 SDK 的发现机制；`full` 模式在配置允许且发现技能时可注册技能工具，`read-only` 白名单不包含 `skills` |
| MCP | `disableMcpSettingsTools: true` 跳过常规 settings 来源；底层仍有加载 Agent 插件贡献的 MCP server 的路径，并非彻底禁用所有 MCP |

`full-task` 的“多轮”指 Agent 连续调用模型和工具，`history` 仅是初始上下文。若只想评测追问内容，可以用单轮案例并覆盖系统提示词允许追问；要评测收到回答后继续完成任务，则需要新增交互机制。

## 真实 Agent 接入与版本标识

### 确保评测经过产品实际使用的逻辑

假设团队修改了公司系统提示词、增加内部知识库工具，并调整了命令审批规则。评测需要让这些修改实际生效。

当前 Runner 直接创建 `ClineCore`，并设置自己的提示词和工具策略。SDK 内部的修改在加载最新构建时可以测到；但仅在 CLI/应用初始化时注册的工具可能缺失，产品提示词或审批规则也可能被覆盖。

建议让产品和评测共用必要的初始化入口：

```text
产品界面 ─┐
          ├→ 公司 Agent 初始化入口 → 魔改 ClineCore
评测器 ───┘
```

评测器负责案例输入、模拟交互和判分，产品入口负责提示词、自定义工具、Skill/MCP 等核心配置。每次运行明确记录哪些配置继承产品默认值，哪些由案例覆盖。审批案例必须启用实际审批路径，不能在 `yolo` 绕过后用一条“同意”消息代替。

这不要求启动完整产品 UI，也不要求立即开发复杂插件系统。先排查魔改位置和当前调用链；若功能已经全部进入 SDK，只需确认配置并补齐运行标识。

### 确认本次到底运行了哪份构建

| 记录项 | 用途 |
|---|---|
| Agent 构建号、发布版本、Git 提交号 | 定位内部发布和对应源码 |
| 实际加载路径 | 发现加载了另一份安装包、旧 `src` 或旧 `dist` |
| SDK/Agent 发布产物 SHA-256 | 确认文件实际一致，提交号本身不能证明本地产物一致 |
| 生效配置及摘要 | 对比提示词、工具集合、审批策略、Skill/MCP 配置；凭据只记录引用 |
| 模型部署标识、采样参数、案例和环境版本 | 区分 Agent 改动与模型、案例、环境变化 |

此前内网曾出现“以为加载新 `dist`，实际加载旧 `src`”的问题。版本标识的目的，就是让通过率变化有可追溯的依据。

## 结果与行为判分：核心设计

建议独立出验证模块：**实际产物和环境状态决定任务是否完成，关键行为约束决定过程是否符合要求，模型评分补充开放式质量维度。** `finishReason: completed` 只代表运行结束，不能单独作为任务成功依据。

### 结果检查器

| 任务类型 | 建议检查功能 | 验收示例 |
|---|---|---|
| 代码开发/修复 | 独立功能测试、回归测试、构建、类型检查 | 原问题修复，边界测试和已有功能均通过 |
| 文件生成/修改 | 存在性、格式解析、字段/内容、指定文件未变更 | JSON 能解析且字段正确，不能只检查文件名 |
| 数据处理 | 行数、去重、统计值、数值容差、关键记录 | 汇总值正确，误差满足案例约定 |
| MCP/业务操作 | 查询服务端实际状态，检查新增/修改和不应改变的数据 | 工单创建成功、负责人正确，没有重复创建 |
| 检索问答 | 关键事实、来源有效性、答案与证据一致性 | 接口参数可在检索返回的内部文档中找到依据 |
| UI 任务 | 页面交互、提交后状态、必要时视觉质量 | 保存后刷新仍保留数据；视觉评分按需增加 |

证据强度要区分：

```text
调用 create_ticket → 工具返回成功 → 服务端存在符合要求的工单
Agent 声称测试通过 → 日志显示通过 → 评测器独立运行验收测试并通过
```

有条件时以最终状态或独立验证为依据。自定义验证脚本覆盖内置断言无法表达的业务逻辑；Agent 自己生成的测试仅作为补充，正式验收测试由案例维护者提供。

### 行为检查器

| 规则 | 建议检查内容 |
|---|---|
| 必须调用 | 必要工具是否被调用，关键参数是否匹配 |
| 禁止操作 | 是否请求或实际执行了禁止动作，分别报告 |
| 调用次数 | 是否重复创建资源、超过约定重试次数 |
| 关键先后关系 | 查询结果返回后才修改，收到批准后才执行 |
| 条件规则 | 缺少必要信息时先追问，拒绝后停止或改用允许方案 |
| 错误恢复 | 失败后按要求重试、换方案或准确报告失败 |
| Skill 使用 | 成功加载指定技能，并满足技能要求的产物或行为 |
| 陈述一致性 | 不得在工具失败或任务未完成时声称成功 |

默认检查关键动作与局部顺序，允许合理探索，不要求每次完整复刻一条参考轨迹。例如读文件顺序不同通常不应扣分，一次工具错误后成功恢复也不应自动判失败。

需要特别区分“请求”和“执行”：工具请求被权限系统阻止，不等于已发生未经批准的执行。事件记录应包含请求 ID、审批结果、工具开始/完成、错误、用户回复及关联关系；顺序检查应以实际事件和因果关系为准。

### 汇总规则与报告

每个案例先声明必要验收条件、关键约束和可选质量维度。整体通过要求必要条件及关键约束全部满足；部分完成程度用于诊断，不能用回答质量、速度等分数抵消关键失败。

| 报告维度 | 表达方式 |
|---|---|
| 完成情况 | 必要条件逐项通过/失败，子目标完成情况 |
| 行为约束 | 每条独立判定，并链接对应事件 |
| 开放式质量 | 分项分数、理由和证据 |
| 执行代价 | 时间、token、工具次数；仅在案例明确预算时作为硬条件 |
| 验证有效性 | 验证成功、验证错误、证据不足 |

报告示例：

```text
案例：修复配置读取，缺路径时询问，写入前必须批准
结果：失败

功能验收：通过，12/12
已有功能回归：通过，35/35
补充路径后继续执行：通过
批准后才写入：失败，事件 18 写入，事件 21 才批准
无关文件未修改：通过
耗时：48 秒
```

如果案例目标是“用户拒绝后正确停止”，没有文件修改也可以通过。每项失败应明确展示“预期、实际、证据位置”。

评分统计同时展示任务通过率、关键约束通过率、执行错误率和判分覆盖率，注明分母；效率优先在相同任务且成功的运行之间比较。网关宕机、缺依赖、验证器故障等单独报告，Agent 构造错误参数造成的失败仍可能计入行为失败，不能把所有工具错误都排除。达到案例预设的任务预算也应按案例规则判定，避免只统计成功运行。

### 内网模型裁判

用于方案合理性、需求覆盖、解释质量、与证据的一致性等难以直接写断言的维度。提供明确评分表，例如需求覆盖、证据一致、未完成项说明各 0～2 分，每项必须附理由和证据位置。

裁判读取任务、相关产物和轨迹，不能只看 Agent 总结；待评内容中的指令作为数据处理，不能覆盖评分规则。固定裁判模型、提示词和评分规则版本，先用人工判过的案例校准；不确定的结果保留人工复核入口。裁判故障不能算 Agent 得零分，裁判用量与被测 Agent 用量分开记录。

### 验证模块自身的验收与重新判分

每个关键案例准备三类材料：已知正确结果应通过；典型错误结果应失败；另一种正确实现也应通过，防止规则绑定某个写法。

验收脚本、预期答案和评分输出由评测器管理，避免 Agent 修改。执行结束后保存产物快照、完整事件、必要业务状态和评分规则版本；支持只重新运行 verifier，无需重新调用 Agent。真实业务服务的状态应及时快照，并记录证据范围，避免事后变化影响复核。

判分模块建议内部顺序：结果断言和验证脚本 → 工具/交互事件断言 → 证据展示 → 归档与重新判分 → 模型裁判和稳定性统计。

## 业界方案对比与借鉴

| 方案 | 官方机制 | 对当前项目的启发 |
|---|---|---|
| Harbor / Rewardkit | 任务执行后运行 verifier，输出单项或多项 reward；支持程序规则和模型/Agent 裁判 | 执行和验证分离，每个案例定义独立验收规则 |
| SWE-bench（代码修复基准） | 检查原失败测试转为通过，以及原通过测试不回归 | 代码任务验证功能和回归，不能仅看文本或改动文件 |
| LangSmith / AgentEvals | 支持 strict、unordered、superset、subset 等轨迹匹配和参数匹配定制 | 检查关键动作，允许多条正确路径；严格匹配仅用于确有必要的流程 |

依据：[Harbor Verifier](https://docs.harborframework.com/core-concepts/tasks/verifier)、[Rewardkit](https://www.harborframework.com/docs/rewardkit)、[SWE-bench 判分实现](https://www.swebench.com/SWE-bench/api/harness/)、[AgentEvals 轨迹评测](https://docs.langchain.com/langsmith/trajectory-evals)。

Harbor 还提供独立 verifier 环境，将声明的产物复制过去验证，便于预装依赖和隔离判分；这种结构值得借鉴，但框架不会自动替我们定义正确的业务验收标准。[独立验证环境](https://docs.harborframework.com/core-concepts/tasks/separate-verifier)

### Harbor 对审批、补充信息、Skill/MCP 的边界

- **审批**：通用 ACP 接入提供允许/拒绝策略；查阅时 Claude Code 原生适配默认 `bypassPermissions`。不能直接视为已有真人审批界面或按案例动态审批脚本。[ACP](https://docs.harborframework.com/core-concepts/agents/acp)、[适配源码](https://github.com/harbor-framework/harbor/blob/main/src/harbor/agents/installed/claude_code.py)
- **补充信息**：支持用户 Agent 模拟对话；查阅时 `--bridge acp` 文档列出的目标 Agent 为 Claude Code、Gemini CLI。这与通用 `--agent acp:...` 接入不同，不能推断 Cline 已兼容。固定阶段任务可用 multi-step，继承对话需要启用恢复并得到目标 Agent 支持。[模拟用户](https://docs.harborframework.com/core-concepts/jobs/simulate-a-user)、[Multi-step](https://docs.harborframework.com/core-concepts/tasks/multi-step)
- **Skill/MCP**：支持本地/Git 技能注入及来源记录，支持声明 MCP 配置；实际识别、注册和执行仍取决于 Agent 适配和服务环境。[Skills](https://www.harborframework.com/docs/run-jobs/skills)、[MCP 教程](https://www.harborframework.com/docs/tutorials/mcp-server-task)

将现有 agent-eval 原样放进 Harbor，不会自动解除 Runner 的交互和 MCP 限制。现阶段建议优先借鉴机制，迁移平台留作后续独立决策。

## 免搭建环境的交付方案

### 首期：Windows 便携包

目标体验：

```text
解压 → 双击“启动评测.cmd” → 浏览器自动打开
     → 首次配置内网凭据 → 选择案例 → 执行并查看判分
```

建议目录（示意）：

```text
AgentEval-Windows/
  启动评测.cmd
  runtime/       内置运行时及必要工具
  app/           评测程序、完整依赖和预构建 Web 资源
  agent/         魔改 Agent 发布产物
  cases/         标准案例、fixture 和验证脚本
  skills/        显式启用的本地技能
  config/        默认网关配置、版本与文件摘要清单
  data/          首次运行创建的案例数据和结果
  logs/          启动诊断和运行日志
```

同事无需安装 Bun、Node、执行依赖安装或克隆仓库。预填网关地址和模型名，个人凭据首次配置并在本机按约定保存，不放入公共包。启动器使用包内路径，检查端口、写入权限和服务健康，防止重复启动，提供清晰错误和诊断导出；升级保留用户数据。

先做完整便携目录，不要求首期单文件 EXE。Bun 支持独立可执行文件，但当前应用有 SDK 动态加载、worker 子进程和资源路径，需按锁定工具链版本验证；尤其当前 worker 使用子进程入口，并不能直接套用 Web Worker 的打包示例。[Bun 独立可执行文件](https://bun.sh/docs/bundler/executables)

当前发布包仍要求首次安装第三方依赖；打包脚本未提供完整 Web 双击启动交付。需要补齐运行时、目标平台依赖、前端资源、worker 入口及启动器，并在目标平台制作和验证，不复制混杂的开发目录。

### 区分系统依赖和案例依赖

| 评测范围 | “无需额外安装”的条件 |
|---|---|
| 文本、结构化输出 | 内置运行时完整，内网模型可达 |
| 文件读写 | 预置文件和所需工具 |
| 指定 Bun/JS 项目 | 随案例预装依赖及验证工具 |
| 内网 MCP | 服务可达、凭据有效；本地服务还需随包提供运行依赖 |
| 任意 Java/Python 等工程 | 需要对应工具链、项目依赖和验证环境，通用包不能自动覆盖 |
| 容器隔离任务 | 本地有容器环境，或由远端执行节点承担 |

首期承诺“预置标准案例解压即用”，对新导入案例先检查所需环境并显示缺项。发布包按 OS/架构区分；在安装包、报告中标明支持范围。免安装评测器不代表可以离线运行所有工程，也不代表可以不访问内网模型服务。

### 后续：内网集中部署

```text
同事浏览器 → 内网评测平台 → 预装工具链的执行节点
                         → 魔改 Agent、内网模型及 MCP
```

团队维护一次服务器，同事使用网址；统一案例、Agent 版本、环境和结果。本地项目需要上传或从内网仓库拉取，也需要设计 Skill/fixture 上传及服务端路径映射。

当前 Web 限制本机访问。集中版需增加登录权限、多用户数据和任务隔离、服务访问配置、资源配额及凭据管理，不能只修改监听地址。便携版适合先交付，集中版适合团队协作和复杂工具链统一运行。

## P0：第一期必须补齐

| 功能 | 建议增加什么 | 最小验收标准 |
|---|---|---|
| 真实 Agent 接入与版本标识 | 增加可配置的 Agent 适配层，加载魔改 SDK/入口；明确继承产品默认配置还是使用案例覆盖；记录构建版本、提交号、产物摘要及实际生效配置 | 指定两个 Agent 构建运行相同案例，能确认加载路径和实际启用的魔改功能 |
| 审批与追问脚本 | 案例定义审批条件及 approve/deny 应答；定义按问题、选项或顺序匹配的用户回复；通过真实回调和会话续跑接口送入 Agent | 覆盖批准、拒绝、补充信息后完成；未匹配交互明确报错，不能静默批准或伪装完成 |
| Skill/MCP 环境声明 | 显式指定本地 Skill、内容摘要、MCP 配置、凭据环境变量和工具白名单；运行前检查加载/连接状态；提供固定返回值的 MCP 测试服务 | 能验证 Skill 已加载、MCP 工具确实调用；缺文件、连接失败与模型答错分别报告 |
| 结果与行为判分 | 保留文本断言，新增文件存在/内容、JSON 字段、测试命令退出码，以及工具名、参数、次数、顺序、禁止调用断言；支持案例验证脚本 | Agent 只声称“完成”但没有产物时失败；审批被拒后继续执行时失败；验证脚本报错单独标记 |
| Windows 便携交付 | 内置运行时、完整依赖、魔改 Agent、预构建 Web 和标准案例，双击启动并提供首次配置和环境预检 | 干净 Windows 机器不能访问公网、不安装开发环境，也能完成真实内网模型调用与结果判分 |
| 内网运行与诊断 | 支持自定义 Headers、内部 CA/代理配置；按目标 OS/架构准备完整离线运行依赖与摘要清单；预检 SDK 导入、网关工具调用协议、Skill/MCP 和必要命令 | 不访问公网即可安装启动，完成本机模拟服务冒烟和内网模型真实工具案例 |
| 运行隔离与完整留痕 | 在现有 worker/工作区隔离上，补齐环境变量白名单、显式配置目录和 MCP 清理；统一 CLI/Web 隔离行为；事件逐条落盘并脱敏 | 超时或异常仍保留已发生的工具、审批、对话和用量记录；案例之间不继承意外状态 |

实现注意：

- 审批脚本必须处理真实审批事件。不能在 `yolo` 绕过审批后，用一条预设“同意”消息代替审批测试。
- 追问脚本首期采用确定性回答，记录匹配规则和实际回复；增加交互次数上限、等待超时和取消处理。Web worker 当前标准输入只处理取消，需要扩展为结构化双向消息协议。
- Skill 配置应显式注入，不能依赖复制整个 `.cline`；MCP 可分别运行“固定响应回归”和“内网真实服务集成”案例。
- 工作区副本不等于操作系统沙箱。执行任意命令或访问服务的案例，应使用受限运行账户、容器或虚拟机，并限定测试服务访问范围。
- 验证脚本由评测器运行，不能由被测 Agent 修改后自行判定通过。密钥使用引用，避免写入案例、轨迹及导出报告。

## P1：第二期提升回归效率

| 功能 | 建议范围 |
|---|---|
| 版本对比 | 同一案例集对比基线与候选构建，展示新增失败、工具行为变化、耗时和 token 差异；按模块统计 |
| 重复运行与稳定性 | 同配置重复 N 次，报告通过率和波动；记录模型部署版本、采样参数及环境摘要，明确无法保证模型完全确定性 |
| 失败分类与恢复 | 在首期基础错误分类上增加聚合分析；只对明确的临时基础设施错误重试，保留每次尝试，避免掩盖 Agent 失败 |
| 归档与重新判分 | 基于首期保存的产物和轨迹重跑验证器；保留旧评分及规则版本，不覆盖原始证据 |
| CI 接入 | 提供稳定的退出码与 JSON/JUnit 报告导出；支持关键案例回归门禁及内网流水线调用 |
| 通用任务与环境准备 | 首期为标准案例提供必要依赖和状态重置；第二期增加通用 setup/teardown，支持 Git 仓库和不同工具链，处理复制规则遗漏的 `.git`、`node_modules` |

## P2：按需求扩展

- **模型模拟用户**：覆盖开放式澄清、需求变化；记录用户模型、persona 和对话，并单独统计其用量。先稳定确定性脚本，再引入模拟用户的不确定性。
- **真人交互评测**：增加等待审批/补充信息状态、Web 应答入口、恢复与审计；用于人工验收，与无人值守批次分开统计。
- **语义评分**：对方案质量等难以写断言的任务接入内网裁判模型，保留评分理由和人工复核入口；不能替代文件与测试验证。
- **内网集中版**：浏览器访问、统一执行节点、多用户协作和权限管理，避免每位同事准备复杂工程环境。

## 建议首期验收集

先准备约 20～30 个小型固定案例，重点包含：

1. 魔改规则、系统提示词和自定义工具确实生效。
2. 审批批准后执行、拒绝后停止或改用允许方案。
3. 缺信息时正确追问，收到预设回答后继续完成。
4. 指定 Skill 生效，并正确调用固定响应和真实内网 MCP 服务。
5. 代码任务实际生成正确文件并通过测试；“口头完成”不能通过。
6. SDK 缺失、网关协议不兼容、MCP 断连、超时取消均可定位，保留失败前轨迹。
7. 验证器能区分已知正确结果、典型错误结果和另一种正确实现；失败项能定位具体证据。
8. 干净 Windows 机器没有 Bun、Node 和仓库源码、无法访问公网，解压双击后可完成预置案例的真实内网评测与判分。

首期完成标准：同一批案例可在内网对两个魔改 Agent 构建独立运行；报告能解释“哪个版本、哪项行为发生变化、依据是什么”；基础设施和验证故障单列，Agent 行为失败按规则计分；同事使用预置案例无需搭建开发环境。
